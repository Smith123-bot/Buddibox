# BuddhiBox — Android product blueprint
**Think Smart. Play Sharp.**
**Review draft · 18 October 2026 · planning only.** Repository inspection found only a minimal README. No game, build, assets, or tests exist; all targets below are proposals, not results. No implementation prompt is authorized until this blueprint is reviewed.

## A. Executive Summary
BuddhiBox is an offline-first, single-player **Android application** with three genuinely playable puzzle types: Find the Difference, Maze Escape, and Word Search in English and Hindi. The first release emphasizes verified content, trustworthy progress, accessible controls, and repeatable release testing over a large catalog. React Native + Expo + strict TypeScript is a suitable default, **conditional** on Android feasibility spikes for Hindi grapheme handling/font shaping, paired-image touch mapping, native dependencies, persistence and release builds. Expo Go is not a substitute for a signed production build. All levels ship locally; no account or server is necessary.

**Initial content gate:** target 8 manually approved Find the Difference pairs, 15 mazes, 10 English and 10 Hindi Word Search boards. This is a *minimum proposed release scope*, contingent on licensed art and content QA; do not advertise unavailable levels. More levels are optional only after the quality gates pass. Estimated level counts and performance targets require device/content validation.

### Risks to investigate before locking solutions
1. **Hindi graphemes:** Hermes `Intl.Segmenter` availability and Indic segmentation behavior vary by runtime; fallback libraries and fonts may split conjuncts differently. Verify with physical Android displays before content production.
2. **Image geometry:** different aspect ratios, contain scaling, pan/zoom and touch slop can make correct taps miss or hit nearby targets. Test transforms and target separation with representative assets.
3. **Art provenance and alignment:** a generated or licensed photo pair does not automatically yield intentional, precisely registered differences. Every pair needs editing, permissions and independent sign-off.
4. **Offline state integrity:** a process death between hint debit and level completion may duplicate rewards or lose progress. Prove transactional/idempotent saves on device.
5. **Expo compatibility and signing:** SDK, Hermes, graphics/gesture/storage/font libraries, Gradle/JDK and EAS signing may constrain implementation. Run an Android development-build and release-build spike.
6. **Interaction accessibility:** tiny image regions and drag-only word selection are exclusionary. Test alternative controls with TalkBack and enlarged text early.
7. **Bundle size/performance:** bundled paired images and fonts increase package size and memory use. Measure a representative pack, not an empty shell.

## B. Product Requirements Document
### Goals, users, needs
Goals: (1) three completable offline games, (2) intuitive 2–7-minute sessions, (3) resilient local resume/progression, (4) bilingual word puzzles with correct visual and logical tokenization, (5) reproducibly installable Android release. Users: casual puzzle players, English/Hindi readers, intermittent-network users and players with motor or visual accessibility needs. No multiplayer, monetization or artificial energy limits in v1. Child-directed positioning/age rating needs legal/product decision before distribution.

### Journeys
- **New player:** install offline → brief optional onboarding/language choice → Home → choose game → instructions/first unlocked level → play → result → next level or Home.
- **Returning player:** Home shows Continue for saved session and per-game progress → resume exact board/player/found items and active time → complete → unlock next level.
- **Interrupted player:** background/process death → restored checkpoint; if incompatible/corrupt, explain recovery and preserve unaffected records.
- **Bilingual player:** choose Word Search pack or switch UI language independently → play either pack with separate progression.
- **Accessibility user:** TalkBack/help → alternative directional or endpoint controls, zoom where needed → complete without relying on gesture/sound/color alone.

### Requirements and nonfunctional contract
P0/P1/P2 definitions are in C. P0 includes shipped content, level validation, saved progress, settings, help, achievements/statistics, airplane-mode gameplay, and verified Android build. P1 improves discoverability/comfort but cannot undermine P0. P2 adds remote/social features only with separate privacy review. Default target Android 9+ is provisional until selected Expo SDK and test devices confirm it. Portrait-first with layouts safe for system insets and small screens; gameplay may offer landscape support only after tested. Performance targets on a specified midrange and low-end device: cold interactive Home <3 s, typical input feedback <100 ms, no noticeable scrolling/drag jank, resume <1 s, no crashes in release acceptance suite. These are gates, not measured facts. Bundle download goal <100 MB subject to art spike. Touch controls ≥48 dp where possible, text contrast ≥4.5:1, font scaling tested to 200%, TalkBack reading order/labels, reduced-motion support and alternate non-drag input. No PII or analytics SDK, no account, no gameplay network request; disclose OS backup/uninstall limitations and local-only progress.

## D. Technical Architecture
**Stack evaluation.** RN + Expo + TypeScript enables shared typed domain logic, fast Android UI iteration, asset bundling and EAS/native build workflows. Limitations: Expo Go cannot validate arbitrary native modules/release performance; Hermes Intl features must be verified; complex high-resolution image zoom, Indic shaping and native file/database access may need Expo-compatible dependencies or a custom development build; OTA updates must not silently change content IDs/schema. Retain this stack if Phase 0 spikes succeed; document a narrowly scoped native Android module if necessary, not a website rewrite.

**Layers / proposed module boundaries** (descriptive paths, not created files): `src/app` navigation/screen composition; `src/ui` themed accessible components; `src/games/{difference,maze,word-search}` pure rules and adapters; `src/domain` shared session/score/level contracts; `src/content` typed versioned manifests and validator; `src/storage` repository/migrations; `src/i18n` UI messages; `assets/{difference,fonts,icons,audio}`. Keep game-specific session types isolated by discriminated game ID and level ID. Screens dispatch typed actions; pure reducers enforce transitions. A lifecycle controller saves checkpoints; database is the durable source of truth. Deterministic content/seed, no runtime network calls. Set SDK/React Native/package versions and lockfile only after compatibility spike. Navigation candidate: Expo Router for file-based typed routes, pending Android back/deep-route verification; React Navigation is fallback if integration warrants it. Use minimal Expo-supported font, haptic, audio and image/gesture packages after build tests; do not promise an untested library.

**Manifest contract:** stable `{gameId, levelId, contentVersion, difficulty, unlockPrerequisite, scoring, payload, validationMetadata}`; level schema validated before packaging and again on save restore. UI strings localized separately from puzzle vocabulary. Game rules never depend on rendered pixel positions except via a tested coordinate adapter.

## G. Find the Difference Design
**Loop:** enter validated pair → inspect two aligned images → tap differences on either image → receive marks on both → optional hint → find all → score/results/unlock. Images must be intentionally edited from same base, same intrinsic width/height and composition; no parallax, crop or automatic generated difference inference. Prefer custom illustrations or licensed editable images. Initial target **8** signed-off pairs, 3/4/5/6 differences across tiers; increase subtlety only within tested visibility limits.

**Level data fields:** stable ID, ordered left/right bundled asset references, intrinsic pixel dimensions/aspect, content/license IDs, difficulty, list of difference IDs each with normalized polygon (or ellipse), visual description, minimum target size/tolerance and optional hint focal point, par active time, hint cost and scoring thresholds. Asset references are statically resolvable, not arbitrary runtime `require` strings. Coordinate transform: both images render with `contain`; compute displayed image rectangle from measured view and intrinsic ratio; reject taps in letterbox; inverse transform pan/zoom and normalize x/y ∈ [0,1]; test polygon/ellipse hit with a **bounded** tolerance (no overlap). Same regions apply to both panels. If image aspect/canvas differs, reject pair at validation rather than guess mapping. Zoom/pan enabled for precision; zoom state isolated from target model. Incorrect taps are only counted inside image bounds, debounced to prevent repeated penalties; found regions idempotent.

Correct tap: distinct ring/marker on both sides, count increment, subtle sound/haptic. Incorrect tap: brief neutral feedback and optional −10 after first 3 misses, no shake barrage. Hint: available credit atomically spent only if unseen region exists, highlight its approximate area for ~2 s without auto-finding. Timer counts active foreground gameplay only, pauses on menus/background; no loss on timeout. Score `max(0, 100×found + max(0,200−floor(200×activeSeconds/parSeconds)) − 50×hints − 10×max(0,misses−3))`; par positive and configured. Stars based on level-specific score thresholds, 1 star for any completion regardless of score; no irreversible fail state. Replay same pair, reset session metrics, preserve best. Alternative accessible list of candidate zones (human-authored descriptions, including distractors, not exposing solutions by default) or zoom-and-scan mode must be usability tested; if alternative mode changes challenge, disclose score treatment consistently. **Validation:** schema/image dimensions, matching aligned landmarks, all region polygons in bounds, nonoverlapping tolerance, targets visibly distinguishable at smallest device size, tap-map automated fixtures and two independent human reviewers locating exactly the declared differences; mismatch blocks release. Packaged assets load without network.

## H. Maze Escape Design
**Loop:** inspect grid → move cardinally from S toward E → optional next-step hint → reach E → results. Odd-sized grid candidate ranges: 7×7 beginner, 11×11 intermediate, 15×15 advanced (cell size must stay readable; adjust dimensions/device). Walls/passages, exactly one start and exit; boundaries explicit. Generate seeded spanning-tree maze via randomized depth-first search, optionally add vetted loops for advanced levels; **freeze and validate** shipped seeds/boards so replay and shortest path stay stable. BFS over traversable cells from S checks exit reachable, shortest-path length and connectivity; reject trivially short, oversized or visually inaccessible levels. A spanning tree guarantees cell connectivity before extra gates; BFS remains mandatory on final serialized board. Initial 15 levels.

One directional button/swipe moves exactly one cell; wall/out-of-bounds produces subtle feedback but no move/time penalty. Swipe threshold and touch cancellation tested; large D-pad always available, optional tap-adjacent cell. Count only successful moves. Exit completion only when player coordinate equals exit; guard against double triggers. Hint computes BFS from **current position**, reveals next route cell without moving, consumes credit only if a next step exists. Active timer follows shared rules. Score `max(0,1000−5×max(0,moves−shortestPathLength)−75×hints+max(0,200−floor(200×activeSeconds/parSeconds)))`; 1 star for completion, thresholds per level for 2/3. Restart resets position/moves/hints-used/elapsed for current run after confirmation. Replay fixed board. Tests: passage connectivity, S/E bounds, impossible-board rejection, wall/bounds collision, exact move counts, exit detection once, BFS hint validity from detours, restart/resume and airplane mode. Difficulty uses path length, branches, dead ends and grid size, not just dimensions.

## I. Hindi and English Word Search Design
**Loop:** choose pack → read word list → select contiguous straight cells → valid target path persists with word mark → find all → results. Initial 10 English and 10 Hindi reviewed boards; first 3 simple (horizontal/vertical forward), next 4 include diagonal/overlap, last 3 may introduce reverse directions after explicit tutorial. Grid roughly 6–10 cells wide; use grapheme-cell width and physical-device legibility to finalize sizes. Lists: 3–6 common age-appropriate words, correct spellings and meaningful theme; Hindi reviewed by fluent readers, English by editor. Avoid ambiguous words, near-identical inflections and visually broken cell tokens. Each level stores ID, language, tokenized grid, targets with normalized display form and explicit start/end/path, allowed directions, difficulty, par/scoring and word-list attribution. Puzzle placement generator may use deterministic seeded backtracking with collision only on identical tokens; cap retries, reject impossible or unintended duplicate occurrences, freeze validated outputs. Fillers come from language-appropriate vetted token pools; ensure accidental target occurrence is either accepted with explicit paths or board rejected. Generated runtime boards are not promised.

**Unicode contract:** ingest input strings → normalize NFC → tokenize with one **pinned and tested grapheme segmenter** → persist token arrays for both words and board → place/compare arrays; renderer receives exactly one token per cell; selection returns cell-token paths; joining tokens and NFC normalization used only for display/validation, never JS `length` or indexing for cell counts. `Intl.Segmenter` with `{granularity:'grapheme'}` is a candidate only after Hermes/Android support and output verification. Fallback must be a pinned Unicode grapheme library with confirmed Indic-conjunct support for the chosen Unicode version, or pre-tokenized curated content generated by a verified build-time tool **and** the same token contract at runtime; generic regex/splitting code is not acceptable. Segmenter mismatch blocks Hindi release. Test cases include क+ि → कि, त+्+र → त्र, क+्+ष → क्ष, क+़ → क़, vowel+anusvara/chandrabindu, ZWJ/ZWNJ and multi-conjunct words; investigate variation across fonts and segmenters rather than assuming one expected grouping fits all. Grapheme boundaries alone do not guarantee cell shaping: verify font, line height, clipping and spoken labels on real devices; reject problematic vocabulary until resolved. NFC is necessary for stable canonical comparison but does not automatically solve conjunct semantics. Hindi is not claimed correct until tested.

Gesture: trace start/end, lock to horizontal/vertical/45° diagonal, show reversible preview and only accept exact stored target path in allowed direction; snap to cell centers, cancel out-of-bounds or invalid angle without penalty. Tap-start/tap-end alternative, plus accessible coordinate/word navigation with spoken full-word labels; overlapping found paths remain distinguishable. Exact target ID credited once; wrong paths clear with gentle feedback. Hint highlights start plus direction of one unfound word; debit only on successful reveal. Score `max(0,100×targets + max(0,200−floor(200×activeSeconds/parSeconds)) − 50×hints)`; completion when all distinct target IDs found, 1 star on any clear, level-specific 2/3 thresholds. Timer foreground-only; fixed replay board; no forced failure. Test every word/path and both selection methods, decomposed vs composed equivalents, reversed-path rules, ambiguous repeats, overlap, tiny/large display, TalkBack, Hindi font rendering and offline clean start.

## J. Shared Systems
**Shared:** typed level registry, unlock prerequisites, session lifecycle (`new → active ↔ paused → completed`), active-time clock, score result contract, hint wallet ledger, save/load, results, achievement evaluation, statistics, sound/haptic preference adapters and localization. **Game-owned:** Difference region geometry, Maze BFS/movement, Word token/grid matching; their reducers must not write another game's counters. Session keys include game ID + level ID + manifest version; impossible transitions rejected. Only one active session at once; prompted replacement; completing a level is idempotent.

Hint economy proposal: 3 initial credits; +1 credit once per first clear of a distinct level, cap 20; hint costs 1. A transaction records spend with session/action ID, prevents repeat charge on re-render, and rejects empty-wallet request without gameplay impact. No purchase needed. Persist after successful move/selection/found difference/hint and on pause/background; restore elapsed *active* time without counting time away. Only completed runs affect best score/unlocks; quitting does not fabricate stats. Achievements use deterministic predicates (first clear in each game, first Hindi clear, 10 total unique clears, no-hint clear); grant once by unique ID. Statistics distinguish attempts, clears, best score, active play duration, hints used, and may recompute from durable run records. Audio/haptics respect system and user settings; settings take effect immediately. If no actual sound assets exist, omit sound toggle until implemented.

## K. Data Model
**Chosen strategy (pending device spike):** Expo SQLite for transactional progress/session/ledger/settings; bundled typed manifests for immutable content. SQLite offers atomic multi-record completion/hint operations and migration support; costs native integration and should be tested in a development build. AsyncStorage alone is simpler but multi-key changes are not atomic; acceptable for low-risk UI preferences only if explicitly separated. SecureStore is unsuitable for bulk gameplay records and offers no backup guarantees. SQLite is local, no remote account. SQLite WAL/transaction behavior and backup policy must be measured in target Expo version.

Conceptual tables: `meta(schemaVersion, installedContentVersion)`, `preferences(language, sound, haptics, reducedMotion, theme)`, `level_progress(gameId, levelId, completedAt, bestScore, bestStars, attempts, unlockState)`, `sessions(sessionId, gameId, levelId, contentVersion, status, serializedState, activeMs, updatedAt)`, `run_records(runId, gameId, levelId, score, stars, hintCount, activeMs, completedAt)`, `hint_ledger(eventId, sessionId, delta, reason)`, `achievement_grants(id, earnedAt)`, `stats_cache(gameId, counters, calculatedAt)`. `daily_challenge_records(challengeId, localDate, outcome, contentVersion)` is **reserved P1 only**, not a displayed or populated P0 table unless a real daily feature ships. Stable composite keys prevent cross-game collision. For privacy, local timestamps are used only for display/reward dedup, not cheating-sensitive daily ranking.

Validate loaded JSON state with game-specific schema and bounds; reject nonexistent levels/invalid hint balances; migrate schema with ordered transactions and fixture tests, maintain stable IDs across app content updates. Idempotent unique event/run IDs make completion and wallet updates safe after retry/process death. Keep last valid checkpoint where feasible; on bad session discard that session with explanation while preserving valid progress; on database corruption attempt recoverable export/backup and require user consent before reset. Reset progress double-confirmed; uninstall may erase data (OS backup policies vary), no cloud recovery promise. Save on meaningful actions and lifecycle pause, not every drag pixel. Packaged content is always available offline. Future OTA content updates require manifest/schema compatibility and rollback plan.

## L. Asset Pipeline
Directory convention: `assets/difference/{level-id}/left.webp`, `right.webp`, and manifest definitions; `assets/maze/` optional themes; `assets/fonts/`, `assets/icons/`, `assets/audio/`; `content/{difference,maze,word}/{language}/` versioned manifests; `content/licenses/` provenance/attribution. Lowercase stable IDs, no renaming after release without migration. Ship image pairs same dimensions/aspect, color profile, framing; source master archived separately, compressed Android-compatible outputs sized for target devices (initial candidate 1080–1600 px long edge, measured for zoom/size), no invisible details after compression. Avoid keeping huge unneeded originals in app bundle. Validate asset exists/decodes, declared dimensions, package size and visual clarity; preload current level and release prior large images to avoid memory spikes.

Difference production: licensed/original base → clone → deliberately edit 3–6 isolated objects → compare alignment with overlay/difference heatmap → draw normalized regions and hint point → automated bounds/overlap and pixel-region checks → two humans independently identify changes on small/large Android displays → license/sign-off record. Heatmap is assistance, **not** proof of gameplay quality. AI-generated imagery still needs rights review and manual alignment. Maze content: seed, generator version, serialized grid, BFS metrics and difficulty review; use original vector shapes. Word content: bilingual vocabulary provenance, fluent Hindi editorial review, canonical-normalization/token report, unintended occurrence scan, device render and voice-label checks. Icons/font/audio licensed or original with attribution; splash/icon follow Android adaptive icon safe zones. No remote assets in core gameplay.

## M. Testing Strategy
**Automated/unit:** TypeScript/lint, schema validation, pure reducer transitions and negative actions, score floor/star thresholds, timer pause/background restoration, idempotent hint/completion, wallet ledger and migration fixtures. Property tests on coordinate transforms (different aspect ratios/zoom/letterbox), maze DFS seeds plus BFS solvability/connectivity/shortest path, movement collisions and hint route, word placement/directions/overlap, Unicode normalization and pinned token corpus, duplicate-word/path rejection. Content validator checks every shipped level, licenses/assets, region bounds, path existence and scoring config. Component tests cover labels/states, input disable/re-enable and no duplicate submissions; navigation tests cover saved-session deep restore, Android back, restart confirmation and results unlock. CI gates on validation/test pass; coverage target for pure game domain ≥90% branch, not a substitute for device QA.

**Emulator:** fresh install/upgrade, route flows, background/kill/relaunch, rotate/small display/font scaling, airplane mode and screen-capture comparison where useful; selected E2E runner only after Expo compatibility spike. **Physical devices:** at least two Android sizes/OS versions including a low-end device; every shipped level completed manually by a tester not its author, all hint paths sampled (every Difference region verified), actual Hindi rendering and TalkBack, drag and alternative input, zoom/tap mapping, audio/haptic settings, release build memory/performance. No test is marked passed until executed with build hash, device, OS, date and results.

**Negative/edge cases:** rapid double tap/completion, hint at zero balance, hint after completion, invalid save JSON, interrupted transaction, missing content reference, letterbox tap, zoomed boundary target, Maze wall/outside/exit re-entry, Word invalid angles/reverse disallowed/duplicate target/ambiguous occurrence/combining-mark variation, no saved session, very large font, clock change, reinstall without backup, no network. Release gates per game: Difference all 8 pairs independently signed off and every target selectable on both screen sizes; Maze all 15 BFS-valid, cleared and hint correct from detours; Word all 20 boards token/path-valid, manually cleared in both languages and Hindi grapheme corpus/render verified on physical Android. Shared gate: clean-install and upgrade offline playthrough, no P0/P1 defects, accessible alternative controls, crash-free acceptance suite, measured performance targets or approved revision. Automation, emulator and device evidence are separately reported; no blanket “thoroughly tested” claim without records.

## N. Android Build Strategy
Development: VS Code, pinned Node/npm and Java/Android toolchain versions after SDK selection; lockfile and setup doc; emulator for rapid loops, physical-device USB/internal distribution for touch, font and performance. Expo Go may preview basic JS but **cannot prove** native module compatibility, app signing or release behavior. Create Expo development builds whenever SQLite/graphics/gesture/font native integrations need validation. Use EAS Build profiles for development, signed internal-testing APK (`preview`) and Play-ready signed AAB (`production`) if distribution pursued. Alternatively local Gradle build only after checking Android SDK/JDK, network/cache and native project compatibility. No assertion that this sandbox currently has SDK, EAS access, signing keys or Play credentials. Verify actual environment in implementation phase; CI cloud build may need account/configuration.

App ID candidate `com.buddhibox.app` needs ownership/availability review. Keep keystore/EAS credentials outside Git; plan secure ownership, recovery and rotation. VersionName user-facing semantic release, monotonically increasing versionCode; test upgrade migrations from prior signed build. Record build hash/version, inspect final permissions, offline clean-install and update, crash logs via adb/logcat (opt-in crash reporting only after privacy review). Test release mode, not dev-only; run device matrix and signed APK install before any Play AAB rollout. If Play: store listing/screenshots/privacy policy, Data safety, age/content rating, asset license review, internal testing then staged release and rollback plan. Uninstall may remove local progress. APK/AAB success and Play approval remain unverified until executed.

## P. Risk Register
| Risk / severity | Mitigation and evidence needed | Fallback / owner decision |
|---|---|---|
| Hindi segmentation/shaping — critical | Pin corpus and Unicode behavior; compare Hermes and fallback on physical devices. | Pre-tokenized validated content plus consistent runtime renderer; postpone affected words, not mislabel broken Hindi as done. |
| Difference art/coordinate mismatch — critical | Same-canvas pair, normalized regions, transform property tests, two-person device QA. | Reduce level count only with explicit scope approval; no fake coordinates. |
| Data-loss/duplicate hints — high | SQLite transactions, idempotent IDs, migration and crash tests. | Disable flawed reward path until corrected; communicate recovery. |
| Expo/native/build mismatch — high | Phase 0 Android dev and release spike with pinned versions. | Compatible native module/prebuild with documented cost; Android-native rewrite only if justified and approved. |
| Bundle memory/size — high | Compressed sample pack, profiling and asset lifecycle. | More efficient art/resolution or validated optional packs (but core remains offline). |
| Accessibility of image/gesture puzzles — high | Alternate modes, TalkBack/zoom tests with users. | Redesign interactions before shipping. |
| Unlicensed/poor vocabulary/art — high | Provenance log, human review, content validator. | Replace content and adjust launch date. |
| Daily challenge/time manipulation — medium | Defer visible feature; schema reserved only. | Later define local-date/timezone/DST/clock rules and validated daily packs. |
| Scope versus polish — high | Phase gates and real content counts. | Negotiate revised scope openly, never ship placeholder games. |
| Device fragmentation/Play policy — medium | Multi-device release tests, policy checklist and signing rehearsal. | Internal APK release first if Play prerequisites unresolved. |

**Unresolved approval decisions:** Android minimum/target devices; art source and budget; 8/15/10+10 launch count; language of full UI versus puzzle packs; sound assets; scoring and hint economy; accessibility mode score treatment; app ID and ownership; child-directed status/age rating; APK-only vs Play distribution; who signs off Hindi vocabulary and art. These are deliberately not silently assumed.

## Q. Final Acceptance Checklist
- [ ] Product owner approves scope, risk responses and unresolved decisions; Phase 0 findings documented.
- [ ] Android app uses pinned RN/Expo/TypeScript stack or approved documented exception; no web substitute.
- [ ] Three games each have validated bundled levels, real completion, scoring/hints/replay and physical-device playthrough evidence.
- [ ] Hindi tokenization, cell rendering, matras/conjunct corpus and selection/matching proven on physical Android; no unsupported blanket correctness claim.
- [ ] Progress, unlocks, achievements, statistics, preferences and interruption recovery verified, including corruption/upgrade behavior.
- [ ] Clean-install, resume and completion work in airplane mode; no account/network dependency.
- [ ] All art, sounds, fonts, words and difference regions have recorded provenance and QA; no placeholder paths or falsely visible levels.
- [ ] Automated, emulator and real-device test reports identify what passed, what failed and what is untested.
- [ ] Accessibility, performance, app size and crash gates measured against selected devices or formally revised.
- [ ] Signed Android APK installs and passes release-mode checks; AAB/Play checks performed if distribution requires them; credentials never in source.
- [ ] Privacy, licenses, versioning, backup limitations and release owner sign-off complete.

**Review boundary:** This is the complete planning blueprint, not proof of implementation or test execution. Review and approve/amend it before requesting any implementation prompt or code.
