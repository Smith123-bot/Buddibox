# Hindi feasibility decision — before content expansion

Inspected Expo 58 / RN 0.88 project: no prior segmentation or bundled Devanagari font. Node 22 in this workspace exposes ICU 78.2 `Intl.Segmenter('hi', {granularity:'grapheme'})`; observed `किताब → कि|ता|ब`, `विद्यालय → वि|द्या|ल|य`, `शक्ति → श|क्ति`, `क्षमा → क्ष|मा`. JavaScript string indexing and `Array.from` are NOT used as cell tokenizers.

**Chosen contract:** authored Hindi/English words are NFC-normalized and segmented *at content-build time* under pinned Node/ICU behavior. The generated, bundled JSON contains word display strings, token arrays, grid token arrays and exact placement paths. At runtime all display, selection and matching operate on these same arrays, with no dependence on `Intl.Segmenter` in Hermes. Validator checks joining tokens reconstructs the NFC word, build-time grapheme boundaries, cell tokens are valid and every declared path is correct. Unsupported words or standalone combining marks are rejected during build. English is uppercase ASCII. Runtime does not dynamically tokenize user input.

**Actual runtime feasibility remains open:** Hermes `Intl.Segmenter` support was NOT measured; it is not required by this curated-content approach. Android default Devanagari font shaping, matra placement, conjuncts, line height, 200% font scale, TalkBack labels and clipping have NOT been verified on emulator/hardware (none available). No font is bundled until its licensing and device behavior can be checked. Five Hindi boards can be structurally validated and shipped for testing, but must **not** be called hardware-rendering validated or release-ready. If any token renders incorrectly on target Android, reject/revise that puzzle or bundle a license-checked font and revalidate before release. No full claim for arbitrary Hindi words.
